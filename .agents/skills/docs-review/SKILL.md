# Documentation Review

## 目的と原則

NEM / Symbol 開発者向けの文書を **技術的正確性・再現性・可読性・安全性** の観点で検査する。
事実、推測、未検証事項を明確に分け、問題は根拠と修正案を添えて指摘する。

レビューだけの依頼では原則としてファイルを変更・コミットしない。修正も依頼された場合は必要な範囲だけ変更する。

## レビュー手順

1. 対象記事・変更差分・PR と関連ドキュメントを確認する。
2. 想定読者、対象ネットワーク、バージョン、実行環境、前提条件を確認する。
3. 公式仕様、実装ソースコード、リリースノートなどの一次情報を優先して照合する。
4. 以下の技術・構成・セキュリティ項目を検査する。
5. 実施できるテストを実行し、成功・失敗・未実行を区別して報告する。

## 技術内容のチェック

- **チェーン区別**：NEM（NIS1）と Symbol の仕様、アドレス、API、トランザクション形式を混同していないか。
- **ネットワーク区別**：mainnet / testnet、ネットワーク ID、エンドポイント、ポートなどの前提が明確か。
- **バージョン整合性**：ノード、REST、SDK、CLI、Docker イメージなどが対象バージョンに適合するか。
- **手順の再現性**：必要ツール、OS、ディレクトリ、権限、コマンド、期待結果が不足していないか。
- **用語**：ブロック確定とファイナライズ、署名とハッシュ、ハーベストと投票、P2P と REST の意味を取り違えていないか。
- **検証範囲**：REST 応答の取得を、暗号学的な独立検証と混同していないか。
- **根拠**：重要な主張に出典があり、リンク先がその主張を実際に裏付けているか。独自の知見や推測は区別されているか。

一次情報にアクセスできない場合は断定せず、未確認であると明記する。
**仕様、URL、コマンド、検証結果を創作しない。**

## Docusaurus / Markdown / MDX のチェック

- Frontmatter（`title`、`description`、`sidebar_position` など）が必要に応じて適切か。
- 見出し階層・見出し ID・内部リンク・画像パス・サイドバーに不整合がないか。
- Markdown / MDX 構文、JSX、コードフェンス、エスケープ処理が適切か。
- 括弧を含む太字の直後に日本語が続き、`**` がそのまま表示されていないか。用語の補足は `**可分性**（divisibility）は` の形にし、修正後の生成 HTML で `strong` 要素になっていることを確認する。
- 外部リンクはアクセスできた範囲と未確認の範囲を区別する。
- 日本語の表記が一貫し、API 名・コードの識別子は正式表記を維持しているか。
- 初学者向け説明が必要な箇所で前提知識が抜けていないか。既存記事と重複しすぎていないか。
- 要点や操作に入る前の長い前置き、見出しの言い直し、回りくどい表現、重複するまとめがないか。必要な条件や理由を残し、読み進めやすくする修正を提案する。
- テンプレート由来の仮文言や誤った編集 URL、サイト URL が残っていないか。

## コード例・設定例・セキュリティ

- 対象 OS とバージョンを明示し、実行可能な例は可能な限り動作確認する。
- ダミー値と実運用値を区別し、未実行のコードは「未実行」と記載する。
- 秘密鍵、ニーモニック、API トークン、パスワードが公開されていないか確認する。
- 秘密情報をログ、スクリーンショット、設定例に含めない。
- 破壊的コマンド、鍵表示、送金などを扱う場合、リスク・前提・確認手順が十分か確認する。
- 第三者ノードの利用と、その情報を独立検証できることを混同していないか確認する。

## ビルド・テスト

リポジトリの scripts と mise 設定を確認したうえで、必要なものを実行する。

```bash
pnpm build
pnpm typecheck
```

依存関係が未導入なら、ロックファイルを尊重して `pnpm install --frozen-lockfile` を検討する。
`pnpm build` の成功は技術内容の正確性や外部リンクの生存を保証しない。
テストを実行できなければ、その理由を報告する。

## 指摘の優先度

| 優先度 | 判断基準 |
| --- | --- |
| 重大 | 秘密情報の公開、資産損失につながる手順、危険な誤案内 |
| 高 | 技術仕様の誤り、実行不能な構築手順、主要リンクの破損 |
| 中 | 前提条件・根拠の不足、誤解を招く文章、構成の問題 |
| 低 | 表記ゆれ、冗長さ、軽微な改善点 |

## 結果の報告形式

問題を**優先度順**に、できる限り次の形式で報告する。

```text
[高] docs/symbol/example.md:42
問題: 対象バージョンと異なる REST API を使用している。
根拠: 対象バージョンの仕様・実装との相違。
修正案: 対象バージョンに合ったエンドポイントに変更する。
```

最後に対象範囲、実施した検証（成功・失敗・未実行）、残った未確認事項を記載する。
問題がなかった場合も「確認した範囲では指摘なし」とし、調査できなかった事項は明示する。
