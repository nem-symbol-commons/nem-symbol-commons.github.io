# Documentation Authoring

## 目的

技術的に正確で、保守しやすい日本語の
開発者向けドキュメントを作成する。

## 作業手順

1. 既存ドキュメントとディレクトリ構造を確認する。
2. 対象機能の仕様と実装を調査する。
3. 一次情報を優先して事実関係を検証する。
4. Markdown / MDX で記事を作成する。
5. 必要に応じてコード例や設定例を追加する。
6. ナビゲーションとの整合性を確認する。
7. pnpm build でビルドを検証する。

## 執筆ルール

- 読者が知りたい事実や、行う操作から書き始める。説明のための前置きを置かない。
- 前提知識や操作の理由は、理解や判断に必要な箇所で補う。初学者向けでも、すべての用語を一から説明しない。
- 「ここでは〜について説明します」「〜することができます」などの回りくどい表現を避け、具体的に書く。
- 見出しの言い直し、同じ内容の繰り返し、定型的なまとめを削る。関連する説明が別記事にあればリンクする。
- 短い段落で自然につなぎ、比較や手順には表・箇条書きを使う。内容に不要な見出しを増やさない。
- 専門用語や識別子は正式表記を保つ。簡潔にするために、仕様の条件や手順に必要な情報を削らない。
- 用語に括弧で補足を付ける場合は、`**可分性**（divisibility）は` のように括弧を太字の外に置く。`**可分性（divisibility）**は` は Markdown で強調と認識されず、アスタリスクが表示されるため避ける。
- 実行可能なコード例を優先する。
- コード例には対象バージョンを明示する。
- 未検証のコマンドを動作確認済みと表現しない。
- NEM と Symbol の仕様差異を明確にする。

表現の例：

> 修正前：ここでは、ノードの情報を取得する方法について説明します。ノードの情報は、REST API を使用することで取得することができます。
>
> 修正後：`GET /node/info` でノードの情報を取得します。

## 完了条件

- 技術的な説明に根拠がある。
- 既存記事との重複が適切に整理されている。
- ドキュメント内の参照先が正しい。
- Docusaurus のビルドが成功している。
